# Вкладка «Алгоритмы»: ручное сопоставление prompt-подходов

## Назначение и владение

Вкладка «Алгоритмы» помогает решить одну алгоритмическую, логическую или аналитическую задачу через одну и ту же настроенную LLM четырьмя способами. Пользователь вручную читает все ответы и их запросы; продукт не выбирает лучший ответ, не выставляет рейтинг и не делает вывод о корректности.

Эта спецификация владеет поведением вкладки, её навигацией, контрактом входа, методами, результатами, trace и путями алгоритмического API. Поведение AI-бариста и его контракт `free|controlled` остаются в [спецификации бариста](../barista-web/SPEC.md); CLI остаётся в [спецификации CLI](../llm-chat-cli/SPEC.md). Алгоритмические запросы не используют кофейные system prompts и не являются вариантом `free` или `controlled`; `/api/chat` не изменяется.

## Навигация и форма

- Навигация содержит доступные с клавиатуры вкладки `Бариста` (`/`, подпись `Неделя 1, Задание 2`) и `Алгоритмы` (`/algorithms`, подпись `Неделя 1, Задание 3`); выбранная вкладка однозначно обозначена визуально и программно. Переход на `Бариста` не меняет его поведение.
- `GET /algorithms` открывает пустую форму. В рамках одной открытой страницы черновик и текущий запуск алгоритмов сохраняются при переходе между вкладками; после обновления страницы, новой сессии или открытия ссылки они не восстанавливаются. Постоянной истории нет.
- Форма содержит обязательное после trim многострочное поле `Условие задачи` (от 1 до 10 000 Unicode-символов). Пользователь в свободной форме помещает в него само условие, форматы и ограничения входа и результата, а также примеры.
- Нет отдельных полей формата, ограничений или примеров, кнопок добавления, массива примеров, лимита их количества, синтаксического разбора или клиентской валидации этих частей условия.
- `Язык` — обязательный select: `Python 3` (значение `python`, начальное), `Java` (`java`) или `C++` (`cpp`). Другие значения недопустимы.
- Enter в многострочных полях добавляет перевод строки. Только кнопка `Получить решения` начинает запуск. У всех полей есть русские labels, понятные сообщения валидации и видимый focus state.
- Нажатие кнопки при валидной форме создаёт неизменяемый снимок `{statement, language}`. В `statement` без предварительного разбора передаётся весь исходный текст условия. Все четыре метода одного запуска получают ровно этот снимок; последующее редактирование формы не меняет работающие запросы или их результаты. Пока цепочки запуска не завершились, повторная кнопка недоступна.
- Следующий валидный запуск создаёт новое поколение и заменяет все результаты и trace предыдущего. Данные разных поколений не смешиваются.

## Общий контракт решения

Каждый метод анализирует свободный текст `statement` для подготовки ответа: условие, форматы и ограничения входа и результата, примеры, известные аргументы и результат. По ним он определяет необходимый интерфейс, но не публикует этот анализ отдельным пересказом.

Если интерфейс обоснован текстом, публичный результат для каждого требуемого решения содержит только следующие части в указанном порядке. У expert-ответа непосредственно перед объяснением допустима короткая метка роли; прямой, пошаговый и meta-ответы начинают сразу с объяснения алгоритма:

- краткое объяснение алгоритма в Markdown;
- вызываемый код на выбранном языке: импорты и внутренние помощники разрешены. Для Python и C++ внешний интерфейс — одна функция; для Java — минимальный класс-контейнер с одним вызываемым методом. `stdin`/`stdout`, `main` и CLI-обвязка запрещены;
- хотя бы один пример вызова и ожидаемый результат.

Не добавляется вводный текст, результат анализа, комментарий о достаточности или однозначности интерфейса, отдельное описание аргументов или return: интерфейс виден из сигнатуры кода. Если интерфейс нельзя обосновать, публичный результат содержит только краткое указание нехватки либо допущения и просьбу уточнить данные; код и пример не выдумываются. Публичный ответ не содержит отдельных секций и не пересказывает исходное условие, форматы входа/выхода, ограничения или examples.

Например, `Условие задачи` может содержать:

```text
Найдите индексы двух чисел, сумма которых равна target.
Вход: nums = [2, 7, 11, 15], target = 9
Выход: [0, 1]
```

Для него допустима Python-сигнатура `def two_sum(nums: list[int], target: int) -> list[int]:`. Это иллюстрация интерфейса, а не предписанные имена или сигнатура для других задач.

Контракт задаёт желаемый формат ответа, но не валидирует его как условие показа. Неполный ответ, отсутствующая секция эксперта или код, не отвечающий шаблону, показываются как получены без автокоррекции. Корректность алгоритма и кода не гарантируется и не проверяется запуском.

## Способы и вызовы LLM

Все методы используют одну и ту же заранее настроенную модель без выбора модели пользователем. Контексты методов независимы: ответ одного обычного метода не передаётся другому. Запуск не содержит автоповторов, скрытых улучшений, отдельного разбора примеров или дополнительных LLM-вызовов.

## Алгоритмические prompt-шаблоны

Все шаблоны алгоритмических prompts являются UTF-8 текстовыми файлами в каталоге `backend/prompts`. Каталог задаётся необязательным полем YAML `algorithms_prompts_dir`; при отсутствии используется `prompts`. Относительное значение разрешается от каталога, содержащего `config.yaml`, поэтому default при обычном расположении конфига — `backend/prompts`.

В каталоге обязательны самостоятельные system-шаблоны `algorithm-direct-system.txt`, `algorithm-step-by-step-system.txt`, `algorithm-experts-system.txt`, `algorithm-meta-prompt-generation-system.txt`, `algorithm-meta-solution-system.txt` и user-шаблон `algorithm-meta-solution-user.txt`. Каждый system prompt описывает только свой метод и не упоминает другие методы. Набор шаблонов, его доступность, UTF-8, синтаксис и успешный контрольный render со всеми разрешёнными placeholder'ами проверяются до готовности API-server принять запрос. Отсутствующий каталог или любой обязательный шаблон, пустой шаблон, ошибка разбора или неизвестный placeholder не позволяют запустить server; диагностика называет ресурс и причину, не раскрывая секреты.

В direct, step-by-step и experts system prompt сначала определяется достаточность данных для интерфейса. При недостатке каждый выдаёт только одно краткое уточнение без решения, шагов, ролей, кода и примера. Только ветка достаточных данных содержит специфичный для метода формат ответа.

Шаблоны рендерятся только при подготовке LLM-вызова с безопасными настройками Go `text/template`, включая `missingkey=error`. System-шаблоны используют `language` и `interface_rule`; user-шаблон второго meta-вызова использует `raw_statement` и `generated_prompt`. Отсутствующее значение при фактическом render делает соответствующий вызов безопасной ошибкой и не отправляет частично сформированный prompt.

Содержимое `raw_statement` и `generated_prompt` считается данными, а не исходным кодом шаблона: оно не может добавлять, переопределять или исполнять template-директивы. После успешного старта обработка запроса не читает prompt-файлы и не меняет загруженные шаблоны; изменения файлов применяются только при следующем успешном старте.

| Метод | Поведение | Фактические LLM-вызовы при успехе |
| --- | --- | --- |
| `Прямой ответ` | Один самостоятельный system prompt требует сразу краткое объяснение, вызываемый код и пример без плана или пересказа условия. | 1 |
| `Решай пошагово` | Один самостоятельный system prompt содержит точную фразу `решай пошагово`, публичные краткие нумерованные проверяемые шаги перед явно отделённым итоговым решением. | 1 |
| `Сначала промпт, затем решение` | Первый новый контекст создаёт самодостаточный prompt, в котором есть общий контракт и распознавание примеров из `statement`. Второй новый контекст получает неизменённый generated prompt, исходный снимок и общий контракт, затем решает задачу. | 2 |
| `Группа экспертов` | Один system prompt требует независимые ответы Теоретика, Практика и Скептика с их собственными code+example; различается аргументация, даже когда оптимальный алгоритм сходится. | 1 |

Обычный успешный запуск выполняет ровно пять LLM-вызовов: `1 + 1 + 2 + 1`. У каждого вызова есть конечное ограничение времени; BFF-ограничение meta-операции допускает оба последовательных вызова. Если первый meta-вызов успешен, а второй завершается ошибкой или истекает, первый результат и trace остаются доступны; второго вызова при ошибке первого нет.

## Бюджеты времени

Алгоритмические вызовы имеют собственный бюджет `algorithm_request_timeout` в backend YAML. Если поле отсутствует, используется `180s`; допустимо только положительное значение не больше `180s`. Значение `request_timeout` сохраняет прежний независимый бюджет `30s` по умолчанию для CLI и AI-бариста и не ограничивает алгоритмы. API-server создаёт отдельный LLM client для алгоритмов с теми же URL, ключом и моделью, но с их бюджетом.

Каждый фактически отправленный алгоритмический LLM-вызов получает полный `algorithm_request_timeout`: у обычных методов это один вызов, у `generated-prompt` первый и второй последовательные вызовы получают отдельные полные бюджеты. Скрытого ограничения в 60 секунд нет. Внешний BFF-бюджет составляет `185000ms` для обычных методов и `365000ms` для `generated-prompt`; он охватывает получение заголовков и чтение тела backend-ответа. Истечение при любой из этих фаз классифицируется как `timeout`. Ограничение чтения входящего BFF-запроса остаётся `10000ms`.

## API-граница

Браузер обращается только к same-origin BFF, а тот — к совпадающему приватному пути Go backend. Каждый endpoint принимает один снимок с полями `statement` и `language` и не принимает структурированные поля условия, ограничений, примеров или `mode`. Приватный backend передаёт исходный `statement` в LLM prompt для внутреннего анализа без воспроизведения этих блоков в публичном ответе.

| Endpoint | Метод | Назначение | LLM-вызовы |
| --- | --- | --- | --- |
| `/api/algorithms/direct` | `POST` | Прямой ответ | 1 |
| `/api/algorithms/step-by-step` | `POST` | Решение с публичными шагами | 1 |
| `/api/algorithms/generated-prompt` | `POST` | Создание prompt и последующее решение внутри одной операции | 2 |
| `/api/algorithms/experts` | `POST` | Ответ группы экспертов | 1 |

Один запуск сразу и параллельно создаёт ровно четыре browser/BFF-запроса, по одному на путь. `generated-prompt` сам выполняет оба последовательных LLM-вызова: браузер не делает отдельный запрос второго шага. BFF и private Go backend до LLM одинаково отклоняют пустые обязательные поля, неизвестный `language`, превышение лимитов полей или размера тела безопасной ошибкой. Учётные данные и приватный адрес LLM недоступны браузеру; ответы не кэшируются.

Промпты, условия, результаты и trace не становятся постоянной историей. Штатные диагностические и прикладные логи не содержат текста задачи, ответов, trace, API-ключей или иных пользовательских данных; содержимое показывается только пользователю на текущей странице.

## Результаты, вкладки и trace

На экране есть четыре вкладки результатов в порядке: `Прямой ответ`, `Решай пошагово`, `Сначала промпт, затем решение`, `Группа экспертов`. По умолчанию активна первая; отображается содержимое только активной вкладки. В подписи каждой вкладки всегда виден её собственный статус: `Ожидает запуска` (`idle`), `Загрузка` (`loading`), `Готово` (`success`) или `Ошибка` (`error`).

Общая кнопка запускает все четыре endpoint независимо от активной вкладки. Переключение вкладок меняет только видимость: не запускает повторный запрос, не сбрасывает и не отменяет запросы или данные других вкладок. Ошибка одной вкладки не скрывает результаты и trace остальных.

- Успешная вкладка показывает полученный текст как Markdown. Объяснения, результаты и generated prompt поддерживают fenced code, списки и GFM-таблицы.
- У каждой вкладки есть закрытый по умолчанию блок `Сырые промпты (N)`, где `N` — число реально отправленных LLM-вызовов. Для каждого вызова показаны порядок и полный упорядоченный массив фактически отрендеренных `messages`: каждое `role` и точное `content` отдельным plain-text представлением с сохранением whitespace.
- Meta-вкладка отдельно сохраняет и показывает первый запрос, его результат/generated prompt как Markdown, полный фактически отправленный второй запрос и итог второго шага. При ошибке второго шага вкладка имеет `error`, но первый шаг и trace доступны.
- Trace не показывает заголовки, API-ключи, backend URL или иной секрет. Raw HTML не исполняется, внешние изображения не загружаются, небезопасные ссылки не создаются. Код и trace в `pre` не интерпретируются как разметка.

Ошибка называет категорию (`проверьте заполнение формы`, `сервис недоступен`, `время ожидания истекло`, `ответ сервиса нельзя прочитать`) и доступное действие, без транспортных деталей, stack trace или секретов. Не-пустой ответ провайдера не отбрасывается только из-за отсутствия ожидаемой структуры.

## Вне области действия

- Автоматическое сравнение, LLM judge, победитель, рейтинг, метрики качества или утверждение, что один подход точнее другого.
- Выполнение, компиляция, тестирование, sandbox/стенд для сгенерированного кода либо проверка примеров.
- Языки кроме фиксированных Python 3, Java и C++, выбор модели, streaming, экспорт, постоянная история и совместное редактирование.

## Acceptance criteria

<!-- ac-section: core-flow -->
### Основной поток и prompt-контракты

- AC-CORE-01: валидное нажатие создаёт один снимок и отправляет ровно один `POST` на каждый из четырёх документированных путей с одинаковыми полями снимка; успешный прогон регистрирует ровно пять LLM-вызовов в распределении `1/1/2/1`; проверка — интеграционный тест с подменённым провайдером.
- AC-CORE-02: BFF и private Go backend принимают только enum `python|java|cpp`; пустое, неизвестное или oversized значение отклоняется до LLM на обеих границах; проверка — параметризованный API-тест каждой границы со счётчиком LLM-вызовов, равным нулю.
- AC-CORE-03: все фактически отрендеренные prompts передают исходный `statement` для анализа условия, форматов, ограничений и примеров; модель не выдумывает данные и определяет интерфейс лишь при достаточных данных. При обоснованном интерфейсе каждый требуемый ответ содержит только краткое объяснение, вызываемый код и пример вызова/результата без пересказа этих блоков; иначе содержит только краткое уточнение. Оба meta-prompts содержат это требование, а второй — неизменённый generated prompt, исходный снимок и общий контракт; проверка — инспекция фактических `messages`.
- AC-CORE-06: для каждого из пяти типов алгоритмического LLM-вызова используется свой загруженный текстовый шаблон; его render получает `language`, `interface_rule` и `raw_statement`, а второй meta-вызов также `generated_prompt`; проверка — интеграционный тест с различимыми шаблонами и инспекцией фактических `messages`.
- AC-CORE-04: прямой метод не содержит подсказки о пошаговом решении; пошаговый содержит точную фразу `решай пошагово` и запрос публичного краткого объяснения; экспертный делает один вызов с требованием трёх собственных функций; проверка — счётчик вызовов и инспекция `messages`.
- AC-CORE-05: Python/C++ prompt требует одну функцию, Java — минимальный класс с одним вызываемым методом без `main`; все варианты запрещают stdin/stdout и CLI и требуют пример вызова при обоснованном интерфейсе; проверка — инспекция фактических `messages`.

<!-- ac-section: form-and-states -->
### Форма, вкладки, состояния и ошибки

- AC-FORM-01: пустое обязательное поле или значение за документированным пределом блокирует запуск и показывает русское сообщение у поля; LLM-вызовов нет; проверка — параметризованный browser-тест.
- AC-FORM-02: одно `Условие задачи` принимает произвольный текст с условием, ограничениями и нулём, одним или несколькими примерами входа/выхода без отдельной UI-структуры или клиентского разбора; проверка — browser-тест с произвольным текстом и инспекция payload, содержащего только исходный `statement` и `language`.
- AC-FORM-03: новый запуск очищает результаты и trace предыдущего поколения до получения новых и не объединяет их; проверка — browser-тест с двумя снимками и различающимися ответами.
- AC-TABS-01: первая вкладка активна по умолчанию; переключение вкладок не создаёт сетевых запросов, не отменяет работающие запросы и сохраняет отдельные result/trace/status всех четырёх вкладок; проверка — browser-тест со счётчиком запросов.
- AC-STATE-01: каждая вкладка независимо проходит `idle/loading/success/error`, а ошибка одной не меняет результаты других; проверка — сценарий с четырьмя endpoint-ответами, один из которых ошибочный.
- AC-ERROR-01: ошибка первого meta-вызова не создаёт второго; ошибка второго сохраняет первый результат и trace, показывая actionable error; проверка — два сценария с подменённым провайдером.
- AC-ERROR-02: не-пустой неполный модельный текст и ответ без обоснованного интерфейса видимы без автодополнения, блокировки или ошибки формата; проверка — fixture без кода и fixture с просьбой уточнить примеры.

### Trace и Markdown

- AC-TRACE-01: блок `Сырые промпты (N)` показывает все и только реально отправленные вызовы, порядок, `role` и дословный `content` с сохранением пробелов и переводов строк; проверка — fixture с отличающимися сообщениями и browser-тест `pre`-содержимого.
- AC-TRACE-02: meta-вкладка содержит два фактических запроса, промежуточный generated prompt и итог, а при ошибке второго — сохранённый первый шаг; проверка — интеграционный и browser-тесты.
- AC-TRACE-03: trace не содержит значений аутентификации, API-ключа или приватного адреса; проверка — интеграционный тест с тестовым секретом и поиск значения в browser-ответе и DOM.
- AC-TRACE-04: trace каждого отправленного вызова содержит точный результат рендера загруженного шаблона, включая подставленные `raw_statement` и, где применимо, `generated_prompt`; проверка — интеграционный тест с whitespace и текстом, содержащим `{{...}}`, затем byte-for-byte сравнение trace с телом запроса провайдеру.
- AC-MARKDOWN-01: объяснение, результат и generated prompt отображают fenced code, список и GFM-таблицу; raw HTML не создаёт DOM-элементы, внешнее изображение не запрашивается, небезопасная ссылка не доступна; проверка — browser-тест с вредоносной Markdown fixture.

### Сквозной чеклист

| Область | Проверяемый критерий |
| --- | --- |
| Adaptive и методы ввода | AC-ADAPTIVE-01: при ширине 320 px и 1440 px форма, labels вкладок и активный результат доступны без горизонтальной прокрутки страницы; длинный код прокручивается внутри блока; проверка — browser-тест обоих viewport. |
| UI-состояния и длинный текст | AC-UI-01: пустая форма, `idle`, `loading`, `success`, `error`, частичный meta-результат и длинный Markdown/trace имеют определённое отображение; проверка — browser-тест fixtures каждого состояния. |
| Доступность | AC-A11Y-01: labels, вкладки, кнопка, раскрытие trace и все поля достижимы Tab/Shift+Tab, а label вкладки объявляет её статус; проверка — keyboard-тест и accessibility tree. |
| Permissions по ролям | N/A: продукт не вводит пользователей, workspace, project или asset-роли. |
| Ошибки API | AC-ERROR-03: network, timeout и некорректный ответ дают безопасную категорию ошибки только затронутой вкладке и действие повторить запуск; проверка — параметризованный тест BFF-ошибок. |
| Деструктивные действия | N/A: функция не удаляет и не изменяет постоянные данные. |
| Security и секреты/PII | AC-SECURITY-01: браузер не обращается к приватному LLM URL, а application-логи и диагностика не содержат prompt, result, trace или секрет; проверка — сетевой browser-тест и захват логов на fixture с тестовым секретом и персональными данными. |
| Read-strategy/свежесть | AC-FRESH-01: два последовательных запуска одного снимка делают новые четыре endpoint- и пять LLM-вызовов; после reload результаты отсутствуют; проверка — счётчик подменённого провайдера и browser-тест. |
| Performance-бюджет | AC-PERF-01: каждый LLM-вызов ограничен конечным ожиданием, а meta-операция получает BFF-бюджет на два последовательных вызова; превышение даёт локальную безопасную ошибку и не создаёт дополнительные вызовы. Входящий запрос сверх server-side ограничений размера или времени отклоняется до LLM; после успешного старта подготовка запроса не читает prompt-файлы. Проверка — интеграционные тесты timeout и oversized request, а также тест удаления шаблонов после старта. |
| Connectivity | AC-CONNECTIVITY-01: потеря соединения даёт локальную actionable-ошибку, а новый запуск после восстановления снова отправляет четыре метода; проверка — browser-тест offline/online с подменённым провайдером. |
| Deep-link и восстановление | AC-DEEPLINK-01: прямой переход на `/algorithms` открывает вкладку и пустую форму; переход между вкладками в рамках открытой страницы сохраняет текущий запуск, reload его очищает; проверка — browser-тест навигации и обновления. |

- AC-PERF-02: отсутствие `algorithm_request_timeout` даёт `180s`; нулевое, отрицательное и значение больше `180s` отклоняются при старте. `request_timeout` не меняет deadline алгоритмического client; проверка — config и wiring-тесты.
- AC-PERF-03: обычный метод не обрезается прежним 60-секундным пределом, зависший провайдер отменяется собственным deadline, а оба meta-вызова получают полный независимый бюджет; второй timeout возвращает первый trace. Проверка — service-тесты с наблюдением deadline context без ожидания реального времени.
- AC-PERF-04: BFF задаёт `185000ms` обычному и `365000ms` meta-запросу; его единый deadline действует на заголовки и body и при истечении в обеих фазах возвращает `timeout`, освобождая reader. Проверка — BFF-тесты с fake timers.
- AC-CONFIG-01: при отсутствии `algorithms_prompts_dir` используются шаблоны из `prompts`; относительный путь разрешается от каталога `config.yaml`, а не от текущей рабочей директории; проверка — config-тест с конфигом и каталогом шаблонов во временном вложенном каталоге.
- AC-CONFIG-02: до готовности server обязательны доступные непустые UTF-8 шаблоны всех пяти типов; отсутствующий каталог/шаблон, невалидный UTF-8, синтаксическая ошибка template или неизвестный placeholder завершают старт с диагностикой и без готового listener; проверка — параметризованный startup-тест.
- AC-CONFIG-03: render без обязательного значения возвращает безопасную ошибку до вызова LLM; `{{...}}` внутри `raw_statement` и `generated_prompt` передаётся дословно; проверка — интеграционный тест со счётчиком LLM-вызовов и инспекцией полученного текста.

## Открытые gap'ы

Открытых Must-gap'ов нет. Гарантируется наблюдаемость фактических запросов и ответов, но не корректность сгенерированного алгоритма или кода.
