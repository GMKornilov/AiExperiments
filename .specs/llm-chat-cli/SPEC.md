# LLM Chat CLI

## Назначение

CLI-приложение демонстрирует управление ограничениями генерации через OpenAI-совместимый HTTP API. При запуске пользователь выбирает флагом `--mode=free|controlled`: оба режима используют отдельный внешний system prompt, но только controlled prompt содержит ограничения формата и дополняется JSON Schema. Для каждого непустого ввода выполняется ровно один API-запрос.

Это ретро-спецификация текущего поведения. Она описывает внешний контракт и не закрепляет детали внутренней реализации.

## Пользовательские сценарии

1. Пользователь создаёт локальный YAML-конфиг, указывает учётные данные, модель и пути к файлам системного prompt и JSON Schema, запускает приложение и вводит сообщение после приглашения `>>> `.
2. В режиме `free` приложение отправляет исходное сообщение с отдельным system prompt AI-бариста без ограничений формата и печатает полученный ответ.
3. В режиме `controlled` приложение отправляет исходное сообщение с усиленным системным prompt, JSON Schema и DeepSeek JSON Output, затем локально проверяет ответ перед выводом.
4. Пользователь вводит пустую или состоящую только из пробелов строку. Приложение не делает сетевой запрос и снова показывает приглашение.
5. API-запрос завершается ошибкой. Приложение выводит диагностическое сообщение с префиксом `Ошибка:` и остаётся доступным для следующего сообщения.
6. Пользователь передаёт EOF. Приложение завершает диалог; при отсутствии ошибки чтения завершение считается штатным.

## Конфигурация

Перед началом диалога приложение читает YAML-файл `config.yaml` из текущей рабочей директории. Конфигурация содержит:

| Поле | Обязательность | Контракт |
| --- | --- | --- |
| `base_url` | да | Базовый URL OpenAI-совместимого API без завершающего `/chat/completions`. |
| `api_key` | да | Секрет для Bearer-аутентификации. |
| `model` | да | Идентификатор модели, передаваемый API. |
| `request_timeout` | нет | Положительная длительность ограничения одного API-запроса; при отсутствии — 30 секунд. |
| `free_system_prompt_path` | нет | Путь к UTF-8 system prompt свободного режима; по умолчанию `prompts/barista-free-system.txt`. |
| `controlled_system_prompt_path` | нет | Путь к UTF-8 system prompt контролируемого режима; по умолчанию `prompts/barista-controlled-system.txt`. |
| `response_schema_path` | нет | Путь к файлу с валидной JSON Schema для контролируемого ответа; по умолчанию `schemas/barista-response.schema.json`. |

Значения обязательных полей не могут быть пустыми или состоять только из пробелов. Значение `request_timeout`, если задано, должно быть больше нуля. Отсутствующий, недоступный, неразбираемый или невалидный конфиг не позволяет начать диалог: приложение сообщает причину в stderr и завершается с ненулевым кодом.

Пример конфигурации без реального секрета:

```yaml
base_url: "https://api.openai.com/v1"
api_key: "<API_KEY>"
model: "gpt-4.1-mini"
request_timeout: 30s
free_system_prompt_path: "prompts/barista-free-system.txt"
controlled_system_prompt_path: "prompts/barista-controlled-system.txt"
response_schema_path: "schemas/barista-response.schema.json"
```

`backend/config.yaml` является локальным секретным файлом и не должен включаться в контроль версий. `backend/.gitignore` также исключает backend build/cache/coverage artifacts. Шаблон конфигурации не должен содержать действующий API-ключ.

## Внешний API-контракт

Для каждого непустого сообщения приложение выполняет один `POST {base_url}/chat/completions` в выбранном при запуске режиме.

Запрос использует заголовки `Authorization: Bearer {api_key}` и `Content-Type: application/json` и JSON-тело следующей формы:

```json
{
  "model": "<model>",
  "messages": [{"role": "user", "content": "<сообщение пользователя>"}]
}
```

Свободный запрос содержит system-сообщение из `free_system_prompt_path` и отдельное user-сообщение. Этот system prompt задаёт только роль AI-бариста и не упоминает JSON, schema, формат, длину или условия завершения.

Контролируемый запрос содержит то же пользовательское сообщение, перед которым добавляется сообщение с ролью `system`. Системное сообщение состоит строго из prompt, прочитанного из `controlled_system_prompt_path`, перевода строки и JSON Schema из `response_schema_path`; код не добавляет иных инструкций. Пользовательский текст передаётся только отдельным сообщением с ролью `user`. Запрос содержит DeepSeek-совместимое `response_format: {"type":"json_object"}`.

После успешного API-ответа приложение разбирает текст как один JSON-объект и валидирует его по внешней JSON Schema. Контракт controlled-ответа: `summary`, ровно три `focus_points` и неизменный `recipe`. `summary` рекомендует действие пользователю напрямую или через фразу «Я рекомендую…»; ассистент не представлен исполнителем кофейного действия. Дополнительные word-limit аннотации схемы также проверяются локально. Ответ не выводится, если он не является валидным JSON, не соответствует схеме или нарушает ограничения длины. Поэтому инструкция из пользовательского сообщения не может ослабить принимаемый приложением формат: конфликтующий ответ будет отклонён независимо от поведения модели.

Успешным считается HTTP-ответ со статусом 2xx. В JSON-ответе приложение ожидает непустой первый элемент `choices` и непустой текст в `choices[0].message.content`; окружающие пробелы текста удаляются перед выводом. Остальные варианты ответа не выводятся.

Не-2xx статус, транспортная ошибка, истечение таймаута, ошибочный JSON, отсутствие вариантов или пустой текст ответа считаются ошибкой одного сообщения.

## Интерактивный интерфейс

Перед каждой попыткой прочитать строку приложение выводит в stdout ровно `>>> `. Успешный ответ выводится с префиксом `<<< `. Режим выбирается один раз при запуске и применяется ко всем сообщениям сессии.

Ошибки отдельных сообщений выводятся в stdout как строка, начинающаяся с `Ошибка:`, и не завершают интерактивную сессию. Ошибки инициализации и чтения входного потока завершают приложение с ненулевым кодом; сообщение об ошибке инициализации выводится в stderr.

## Запуск, сборка и состав поставки

Go-модуль расположен в `backend/`, а команда — в `backend/cmd/llm-chat`; приложение может быть запущено средствами Go либо собрано в исполняемый бинарный файл для целевой ОС и архитектуры. После запуска бинарного файла его рабочая директория должна содержать валидный `config.yaml`; относительные пути prompts и schemas разрешаются от backend cwd.

Логическая структура проекта разделяет пользовательскую команду, чтение конфигурации и интеграцию с LLM API. Эта граница нужна для изолированной проверки контрактов конфигурации и API; точные имена каталогов и компонентов не являются частью спецификации.

## Ограничения и вне области действия

- Контекст диалога между сообщениями не сохраняется и не передаётся API: каждое сообщение является независимым запросом с одной пользовательской репликой.
- Потоковая выдача, Markdown-рендеринг, история, выбор ролей пользователем и tool calling не поддерживаются.
- Оба системных prompt и JSON Schema загружаются при старте приложения; их содержимое можно менять без перекомпиляции. Schema используется только в controlled-режиме.
- Повторные попытки, автоматическое переключение провайдера и хранение токенов вне локального YAML-файла не поддерживаются.
- Форматы конфигурации, отличные от YAML, и интерактивное изменение настроек не поддерживаются.
- Кроссплатформенная упаковка, автообновление и установка бинаря не входят в контракт приложения.

## Acceptance criteria

<!-- ac-section: core-flow -->
### Основной поток

- AC-CORE-01: при валидном конфиге и одной непустой введённой строке приложение выполняет ровно один `POST` на `{base_url}/chat/completions` с указанными заголовками и полями `model` и `messages[0]`; проверка — тест с локальным HTTP-сервером, считающим запросы и проверяющим метод, путь, заголовки и JSON-тело.
- AC-CORE-02: при ответе 2xx с `choices[0].message.content` равным `" Привет! "` stdout содержит строку `<<< Привет!`; проверка — тест с подменённым API и захватом stdout.
- AC-CORE-03: при пустом вводе или вводе только из пробельных символов число HTTP-запросов равно нулю; проверка — тест с локальным HTTP-сервером.
- AC-CORE-04: для двух непустых строк ввода приложение делает ровно два независимых запроса выбранного режима; пользовательский текст соответствует исходной строке; проверка — тест с локальным HTTP-сервером.
- AC-CORE-05: режим `free` содержит отдельный system prompt без упоминаний JSON/schema/формата и не содержит `response_format`; режим `controlled` содержит другой system prompt с внешней JSON Schema и `response_format.type = "json_object"`; проверка — тесты с локальным HTTP-сервером и разбором тела запроса.
- AC-CORE-06: controlled-ответ выводится только после успешного JSON-разбора, проверки внешней JSON Schema и word-limit аннотаций; проверка — тесты валидного ответа, лишних полей, неверных типов, неверного числа рекомендаций и превышения каждого лимита слов.

<!-- ac-section: configuration -->
### Конфигурация и секреты

- AC-CONFIG-01: отсутствие любого из `base_url`, `api_key`, `model`, либо значение только из пробелов, приводит к завершению до первого приглашения с ненулевым кодом и диагностикой причины; проверка — параметризованный запуск с пятью невалидными конфигами.
- AC-CONFIG-02: при отсутствии `request_timeout` ограничение одного запроса составляет 30 секунд, а при заданном положительном значении используется заданная длительность; проверка — модульный тест чтения конфигурации и тест API, намеренно не отвечающего дольше установленного малого таймаута.
- AC-CONFIG-03: в репозитории отсутствует действующий API-ключ в отслеживаемых файлах, а локальный `config.yaml` исключён из контроля версий; проверка — поиск по отслеживаемым YAML-файлам и проверка правил игнорирования Git.
- AC-CONFIG-04: отсутствующий или пустой free/controlled system prompt и отсутствующий или невалидный JSON-файл schema приводят к диагностике до первого API-запроса; при отсутствии путей используются документированные default-файлы; проверка — параметризованные тесты загрузки.

<!-- ac-section: errors -->
### Ошибки и восстановление

- AC-ERROR-01: при каждом не-2xx ответе, ошибке соединения, таймауте, невалидном JSON, пустом `choices` или пустом первом тексте stdout получает диагностическое сообщение с префиксом `Ошибка:`, после чего приложение принимает следующее сообщение; проверка — параметризованный тест, в котором после ошибочного ответа локальный сервер возвращает успешный.
- AC-ERROR-02: при EOF после обработки последней строки приложение завершается без сообщения об ошибке чтения и с нулевым кодом; проверка — интеграционный тест с конечным входным потоком.
- AC-ERROR-03: ответ модели, нарушающий controlled-формат, выводится как диагностическая ошибка и не печатается с префиксом `<<<`; интерактивная сессия продолжает работу.

<!-- ac-section: interface -->
### Консольный интерфейс

- AC-CLI-01: перед каждым чтением строки stdout содержит точное приглашение `>>> `; проверка — тест захвата stdout для ввода из двух строк и EOF.
- AC-CLI-02: `--mode=free` и отсутствие `--mode` выбирают свободный режим, `--mode=controlled` выбирает контролируемый режим, а другое значение завершает запуск с диагностикой; проверка — тест разбора аргументов.
- AC-CLI-03: успешный ответ выводится с префиксом `<<< ` и заканчивается переводом строки; проверка — тест точного содержимого stdout.

## Известные отклонения и долг

Перечисленные ограничения являются намеренными границами текущего продукта, а не известными дефектами.

- Документация запуска не синхронизирована с фактической командой CLI и может предлагать несуществующий способ запуска. `owner: Agent`. Блокирует воспроизводимый старт приложения новым пользователем; требуется привести пользовательскую инструкцию по запуску и сборке в соответствие с фактической командой.
- Диагностика не-2xx ответа может включать неочищенное тело ответа провайдера. `owner: Agent`. Это может раскрыть данные, возвращённые внешним API, в терминале; требуется определить безопасный формат диагностик без включения тела ответа целиком.
