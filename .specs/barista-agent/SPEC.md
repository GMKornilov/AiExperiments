# Агент-бариста: web-чат с памятью в ОЗУ

## Назначение и границы

Это единый SSOT для учебного web-приложения AI-бариста. Оно принимает вопрос о
кофе, передаёт его отдельному агенту-бариста, получает ответ LLM и показывает
полную переписку. Спецификация заменяет прежние отдельные спеки web-бариста,
CLI, структурированного ответа, температуры, моделей и алгоритмов.

В области действия: web-чат с несколькими диалогами, памятью в ОЗУ, admin-просмотром
логов по ID и наблюдаемостью. Вне области: CLI, structured output, настройка
температуры, сравнение и ручной выбор моделей, алгоритмические задания,
постоянное хранилище, аккаунты и аутентификация.

Реализация удаляет CLI и прежние задания из UI, backend, конфигурации, документации и
тестов. Существующие Go/Next.js, BFF, HTTP-клиент, безопасный Markdown и диагностика
переиспользуются там, где соответствуют этому контракту.

## Роль агента и данные диалога

Агент-бариста — самостоятельная доменная сущность. Только он владеет ролью,
снимком LLM-настроек, историей диалога, сборкой контекста и одним обращением к
LLM на попытку. Web-интерфейс передаёт агенту выбранный диалог и сообщение,
отображает его состояния и не вызывает LLM напрямую.

- Агент консультирует о зёрнах, помоле, рецептах и улучшении напитка. Он различает
  рецепт с нуля и улучшение существующего, делает разумные допущения при нехватке
  данных и отвечает на языке последнего вопроса пользователя.
- В контекст каждого вызова входят system prompt снимка, завершённые пары `user` /
  `assistant` выбранного диалога и текущая user-реплика. При retry текущая реплика
  включается ровно один раз. Ошибочная реплика не получает assistant-пару и не входит
  в другой вызов, пока сама не станет retry.
- Диалог и логи принадлежат одному браузерному сеансу. Обычный chat API не выдаёт
  данные другого браузера; исключение — `/admin` по точному ID без аутентификации.
  Идентификатор диалога — непрозрачное случайное значение не менее 128 бит; он виден
  в клиенте небольшим текстом.
- Серверные диалоги, снимки и журнал существуют только в памяти backend: refresh
  сохраняет принятую историю, а перезапуск сервера стирает эти данные. Клиент хранит
  только локальное отображение и непринятый optimistic-ввод.

## Диалоги и основной сценарий

При первом открытии чат пуст. Левая sidebar, как у обычного LLM-чата, содержит
кнопку «Новый диалог» и диалоги текущего браузера, упорядоченные по последней
активности. Создание сразу открывает пустой диалог. До первого сообщения его
название — «Новый диалог»; затем это первые 60 Unicode-символов первого сообщения
пользователя. Ручного переименования нет.

Основная область показывает всю историю выбранного диалога. Длинные названия и
сообщения переносятся либо прокручиваются в собственном блоке, не расширяя страницу.
При переключении история не меняется. После refresh открывается последний выбранный
диалог, если он ещё есть; иначе — самый новый или пустое состояние.

Отправка непустого сообщения до 4 000 Unicode-символов немедленно добавляет локальный
optimistic user bubble со статусом ожидания, до завершения сетевого запроса. После
принятия backend эта реплика становится persisted-записью диалога и агент запускает
одну попытку. Пока агент ждёт LLM, отправка из этого браузерного сеанса недоступна,
но переключение диалогов доступно. При успехе к тому же диалогу добавляется один
assistant bubble. На одну попытку агент делает не более одного upstream-вызова и не
выполняет автоматических retry.

При timeout, недоступности сети/backend/LLM или невалидном ответе user bubble остаётся
со статусом ошибки и безопасным понятным текстом. У каждой user и assistant bubble есть
иконка с доступной подписью «Копировать сообщение»; только у ошибочной user bubble есть
«Повторить отправку». После ошибки composer этого диалога заблокирован до retry — это
технический default, сохраняющий линейный порядок контекста. Retry повторно использует
ту же реплику и не добавляет её копию.

Если сеть оборвалась до принятия backend, ошибка остаётся только local optimistic bubble
и после refresh исчезает. Если backend уже принял реплику, она восстанавливается после
refresh в последнем server-состоянии. Перед retry клиент сверяет это состояние: успешный
assistant-ответ отменяет retry, pending-реплика не запускает параллельную попытку, а
persisted error повторяется. При обрыве после upstream ровно-один вызов у провайдера не
гарантируется; новая retry-попытка возможна только после этой сверки. Local-only bubble
повторяется с тем же client message ID; backend дедуплицирует его принятие, но не обещает
ровно-один upstream-вызов.

Удаление диалога требует явного подтверждения и не имеет undo. После подтверждения
backend отменяет незавершённый вызов, стирает диалог, его снимок и логи в ОЗУ; поздний
ответ не восстанавливает диалог и не появляется в интерфейсе. Пустой или слишком длинный
ввод не создаёт реплику и не вызывает LLM.

## Конфигурация и снимки

Есть два YAML-файла:

- **Backend-конфигурация** читается при старте сервиса и содержит service-настройки,
  путь к LLM-конфигурации и `log_text_payloads`. Значение флага по умолчанию —
  `false`; путь к LLM YAML разрешается относительно backend YAML, изменение этого
  файла применяется после перезапуска. `log_text_payloads` — единственный источник
  этого режима; прежний env `LLM_LOG_PAYLOADS` его не переопределяет.
- **LLM-конфигурация** содержит endpoint провайдера, модель, credential, timeout
  запроса и путь к system prompt. Путь к prompt разрешается относительно этого
  YAML-файла.

Перед созданием каждого нового диалога сервис заново читает LLM-конфигурацию и prompt,
проверяет их и сохраняет неизменяемый снимок. В снимок входят параметры, влияющие на
ответ, включая credential; он существует только в памяти backend. Изменения LLM YAML
или prompt влияют лишь на следующие диалоги. При невалидной LLM-конфигурации или prompt
диалог не создаётся, а пользователь видит безопасную ошибку; старые диалоги продолжают
работать со своими снимками. Ошибка backend-конфигурации не даёт сервису стать готовым.

Ни model picker, ни runtime-замена модели не предлагаются. Технический default timeout
LLM — 30 секунд, если он не указан в LLM-конфигурации.

## Внешние контракты

Браузер обращается только к same-origin BFF, а тот — к приватному backend. Ответы не
кэшируются. Browser API предоставляет операции создать, перечислить и открыть свои
диалоги, удалить диалог, отправить или повторить сообщение, а также передать событие
наблюдаемости. Операция отправки возвращает итоговую assistant-реплику или безопасную
категорию ошибки. Формат не раскрывает credential, system prompt, приватный URL или
сырую ошибку провайдера.

`/admin` — отдельная страница без аутентификации, доступная независимо от браузерного
сеанса. Она не перечисляет диалоги сервиса или чужого браузера: пользователь вводит точный
ID, после чего видит его логи. Несуществующий или удалённый ID даёт нейтральное «данные не
найдены». Обновление доступно по кнопке и автоматически каждые 5 секунд. Записи frontend/BFF
и backend показаны отдельными визуальными группами, внутри каждой — по времени.

## Наблюдаемость

Все продуктовые действия пишутся в центральное хранилище логов в ОЗУ и в server console:
создание, выбор и удаление диалога, отправка, retry, копирование, admin lookup и ручное
обновление, валидация, загрузка конфигурации, вызов LLM, отмена и каждый success/failure
backend. Frontend-события передаются через BFF; источник записи устанавливает сервер.
Автоматическое polling-чтение `/admin` не создаёт новую лог-запись и не записывает заново
уже полученную историю.

У каждой записи есть timestamp, `source` (`frontend` или `backend`), событие, результат,
correlation ID, а при наличии — ID диалога и сообщения. Завершённые операции содержат
длительность в миллисекундах, ошибки — безопасную категорию. Ошибка до создания диалога
логируется с correlation ID без ID диалога и доступна через console, поскольку admin не
имеет глобального списка.

При `log_text_payloads=false` тексты сообщений, ответов и prompt не записываются. При
`true` логи выбранного диалога могут содержать user/assistant-тексты; не логируются
credential, Authorization, содержимое конфигураций, system prompt и сырые заголовки.
Перед записью из текста удаляются значения credential текущего снимка. Admin показывает
нейтральный индикатор включённого режима.

Удаление диалога удаляет его записи из memory-store и `/admin`, но не изменяет уже
выведенные строки server console. Перезапуск сервера очищает только memory-store.

## Состояния и обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| Нет диалогов | Пустая область с действием «Новый диалог». |
| Новый диалог | Sidebar показывает выбранный диалог и ID; его история пуста. |
| Ожидание | User bubble уже виден, статус объявлен assistive technology, отправка недоступна. |
| Ошибка попытки | Тот же user bubble помечен ошибкой; доступны copy и retry, assistant bubble отсутствует. |
| Backend/LLM недоступен | Пользователь видит «Не удалось получить ответ. Повторите отправку.» без внутренней причины. |
| Offline/online | При offline попытка заканчивается ошибкой без авто-retry; после восстановления доступен retry. |
| Удаление во время ожидания | После подтверждения запрос отменён, чат исчезает и поздний результат игнорируется. |

## Acceptance criteria

- **AC-AGENT-01.** Роль, снимок, история, контекст и вызов LLM доступны только через
  контракт агента-бариста; browser не вызывает провайдера. Проверка: интеграционный тест
  с fake agent и сетевой browser-тест.
- **AC-CORE-01.** Новый диалог получает снимок текущих LLM YAML и prompt; изменение
  обоих файлов между созданием двух диалогов меняет ответы только второго. Проверка:
  интеграционный тест с двумя fixture-конфигурациями и подменённой LLM.
- **AC-CORE-02.** Два сообщения одного диалога передаются LLM как system, user,
  assistant, user; сообщения другого диалога отсутствуют. Текущая или retry user-реплика
  присутствует ровно один раз. Проверка: inspection fake-provider запроса.
- **AC-CORE-03.** После ошибки composer блокирует новое сообщение. Retry последней
  ошибочной user-реплики даёт один assistant bubble без второго user bubble. Проверка:
  browser-тест с ошибкой, затем успехом fake backend.
- **AC-CORE-04.** При потере ответа клиент перед retry получает server-состояние: success
  не повторяется, pending не получает параллельную попытку, persisted error повторяется.
  Проверка: интеграционный тест обрыва BFF после accepted, pending и success.
- **AC-CORE-05.** Удаление ожидающего диалога отменяет вызов; после подтверждённого
  удаления он отсутствует в sidebar, browser API и `/admin`, а поздний fake-provider
  ответ не создаёт запись. Проверка: интеграционный тест управляемой задержки.
- **AC-UI-01.** Sidebar создаёт и выбирает новый диалог, показывает title из первых
  60 Unicode-символов первого вопроса и ID. Copy доступен у user/assistant bubbles,
  retry — только у ошибочной user bubble. Проверка: browser-тест.
- **AC-STATE-01.** Browser видит только свои диалоги; refresh восстанавливает принятые
  сервером сообщения, перезапуск сервера возвращает пустое состояние. `/admin` по точному
  ID остаётся исключением. Проверка: browser и интеграционный тест двух сессий.
- **AC-CONFIG-01.** Невалидный backend YAML не запускает сервис. Невалидный LLM YAML,
  отсутствующий или пустой prompt не создаёт диалог и не вызывает LLM; прежний диалог
  отвечает по снимку. Проверка: параметризованный startup и интеграционный тест.
- **AC-OBS-01.** Для create, select, send, retry, copy, delete, config-read и LLM
  start/finish/error есть коррелируемая запись с source, result и dialog ID, когда он
  существует. Проверка: сценарный тест и сравнение memory-store с console capture.
- **AC-OBS-02.** При выключенном флаге capture логов не содержит fixture prompt,
  answer, system prompt, credential или Authorization; при включённом видны message-texts,
  а credential удалён и admin показывает индикатор режима. Проверка: поиск fixture-строк
  в обоих режимах.
- **AC-ADMIN-01.** `/admin` не выдаёт список ID и по точному ID показывает отдельные
  frontend/backend группы. Ручное обновление отражает новые записи; polling делает чтение
  каждые 5 секунд без создания записей о самом polling. Проверка: browser-тест с fake timers.
- **AC-TIMEOUT-01.** Зависшая LLM отменяется по timeout снимка (30 секунд default),
  даёт error bubble и не вызывает второй upstream-запрос. Проверка: интеграционный тест
  с контролируемым clock/context.

## Проверка после реализации

Проверить AC автоматическими unit/integration/browser-тестами, вручную пройти создание,
переключение, refresh, error/retry, delete во время ожидания, изменение LLM-конфига и
просмотр `/admin` с обоими положениями text-log флага. Отдельно захватить server console
с fixture credential и убедиться, что его нет в выводе.

## Контракт реализации

Реализация завершена 2026-09-07; результаты проверок — в [VERIFICATION.md](VERIFICATION.md).
Backend хранит сессии и выбранный диалог в ОЗУ;
BFF передаёт случайный идентификатор браузера из HttpOnly same-site cookie через
`X-Session-ID`. Correlation ID передаётся через `X-Request-ID`.

- `GET /api/dialogs` → `{dialogs, selected_dialog_id}`; `POST /api/dialogs` → диалог.
- `GET /api/dialogs/:id` → диалог; `DELETE` → `204`.
- `POST /api/dialogs/:id/select` → `204`.
- `POST /api/dialogs/:id/messages` с `{client_message_id, text}` → диалог.
- `POST /api/dialogs/:id/messages/:messageId/retry` → диалог.
- `POST /api/events` принимает разрешённые события UI, без произвольного текста.
- `GET /api/admin/logs?dialog_id=...&action=lookup|refresh|poll` →
  `{found, log_text_payloads, logs}`; `poll` не создаёт события.

Диалог: `{id, title, created_at, updated_at, messages}`. Реплика:
`{id, client_message_id?, role, text, status, created_at, error_category?}`;
`status` — `pending`, `success` или `error`. Ошибка HTTP:
`{error: {category, message}}`, где категории включают `config`, `validation`,
`network`, `timeout`, `provider`, `invalid_response`, `not_found`, `busy`.
Принятые сообщения выполняются независимо от разрыва клиентского соединения;
их отменяют timeout, удаление диалога и завершение сервиса.
