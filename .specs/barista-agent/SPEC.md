# Агент-бариста

## Назначение, scope и владение

AI-бариста — веб-агент, который ведёт несколько чатов, организованных в
проекты, и отвечает пользователю в границе его browser-сеанса. Текущий
продуктовый контракт состоит из этой базовой спецификации,
[спецификации слоёв памяти](../memory-layers/SPEC.md),
[спецификации персонализации](../personalization/SPEC.md) и
[спецификации инвариантов](../invariants/SPEC.md).

Эта спецификация владеет общим продуктовым поведением: назначением агента,
сеансовой изоляцией, жизненным циклом чатов, базовыми UI- и error-правилами.
`memory-layers` — единственный authoritative владелец жизненного цикла и
принадлежности проектов, трёх слоёв памяти, состава main prompt, memory
extractor-а, панели памяти и очистки. Эта спецификация владеет composer-ом и
отображаемыми названиями чатов и проектов. При любом противоречии по памяти и
жизненному циклу проектов приоритет имеет `memory-layers`; правила не
дублируются здесь. `invariants` — единственный владелец static ограничений,
pre/post-validation, repair/refusal lifecycle, внешней категории
`invariant_validation` и панели правил.

В scope: агентский чат, проекты как пространство организации чатов, основной
ответ, восстановление принятого состояния, удаление и безопасная диагностика.
Исторические контракты хранятся в [каталоге deprecated](../deprecated/README.md)
и не описывают доступное поведение.

## Основной пользовательский сценарий

Пользователь создаёт или выбирает проект, затем создаёт или выбирает чат этого
проекта и отправляет сообщение. Агент принимает сообщение, формирует ответ и
показывает его в этом чате. Каждый чат принадлежит одному проекту; диалоги из
других проектов не смешиваются в интерфейсе или в контексте ответа.

Пока сообщение ожидает полного цикла ответа, повторная отправка в том же чате
недоступна. Полный цикл включает обязательный invariant pipeline и обновление
памяти, определённые `invariants` и `memory-layers`; main LLM result не
показывается отдельно до завершения этого цикла.

В composer-е Enter отправляет сообщение, у которого после trim остаётся хотя бы
один символ, а Shift+Enter вставляет перенос строки. Enter во время pending не
создаёт новую отправку. Это поведение доступно с клавиатуры и не меняет текст до
явного действия пользователя.

### Идентификатор чата

Над composer-ом выбранного чата отображается его неизменяемый ID и кнопка
копирования. Кнопка копирует ровно значение ID без визуальной метки; она
доступна с клавиатуры и сообщает успешный либо неуспешный результат без
добавления ID в status-объявление. Панель не отображается, пока чат не выбран.

### Название чата

После первого final accepted user/assistant pair для чата запускается ровно
один независимый `text` LLM-вызов названия с действующими настройками и prompt
для text-модели. Вызов не задерживает уже принятый response. Он возвращает
trimmed plain-text title длиной не более 60 Unicode-символов на языке первого
user message. При technical validator error и для непринятого candidate
title-вызов не создаётся.

Если вызов title завершился ошибкой, вернул пустое/невалидное значение или
значение длиннее 60 Unicode-символов, названием становится первые 60
Unicode-символов первого user message. Retry, второе и последующие сообщения,
refresh и restart не запускают title-вызов повторно. Название и его результат
сохраняются и остаются изолированными browser-сеансом.

Внешне полезный `title_status` имеет значения `pending`, `success` и `fallback`:
он позволяет UI показать временное состояние и получить итог при polling или
повторном чтении. `fallback` не раскрывает внутреннюю ошибку text-модели.
Если основной ответ или invariant validation завершается технической ошибкой,
пользователь видит понятную категорию ошибки и может вручную повторить эту
попытку. Автоматического повтора нет. Template refusal из `invariants` —
принятый assistant response, а не техническая ошибка.
Удаление чата или проекта требует подтверждения; последствия удаления проекта
и памяти определяет `memory-layers`.

## Внешнее состояние

Внешнее состояние browser-сеанса включает список проектов с названиями,
выбранный проект, чаты каждого проекта с названием и `title_status`, выбранный
чат, принятые сообщения и статус последней попытки. Чтение возвращает только
состояние владельца текущей cookie; мутации возвращают подтверждённое
server-состояние или безопасную категорию ошибки.

Создание, выбор и удаление проекта/чата, отправка и ручной retry не раскрывают
внутренние ошибки провайдера или credentials. Действия памяти и их состояния
определяет `memory-layers`, а invariant pipeline и его outcomes — `invariants`.

Пользователь может явно переименовать выбранный проект. PATCH принимает title
после trim: он обязателен, не пуст и содержит не более 100 Unicode-символов.
Невалидное значение возвращает безопасную validation error, а ошибка сохранения
— безопасную storage error; в обоих случаях прежнее название остаётся. Успешное
переименование сохраняется, не меняет чаты или память и изолировано текущим
browser-сеансом. Автоматическое название проекта в MVP отсутствует.

### Журнал чата

Страница `/admin` принимает точный ID чата, скопированный из его панели, и
показывает журнал этого чата. Поиск остаётся доступен без browser-сеанса и не
перечисляет чаты; неизвестный либо удалённый ID возвращает нейтральное «Данные
не найдены». Записи чата доступны до перезапуска backend и включают вызовы LLM
с корреляционным идентификатором, результатом, категорией ошибки и длительностью
без credentials. Для журнала BFF прозрачно передаёт backend payload без
семантической валидации полей и не превращает найденный журнал в ошибку ответа.
Записи invariant validation — исключение: они содержат только безопасные
метаданные по контракту `invariants`, без prompt, payload, facts, candidate или
причины verdict-а.

Текстовые поля prompt и payload в остальных допустимых записях журнала
отображаются в читаемом виде:
семантические `\n`, `\r` и `\t` рендерятся соответственно переносами строк и
табуляцией, в том числе когда журнал содержит их с дополнительным уровнем JSON
экранирования. Это только представление: исходный журнал и API payload не меняются.

<!-- ac-section: states-and-errors -->
## Состояния и наблюдаемость

Пустой проект явно показывает возможность создать чат. Пустой чат показывает
composer и не содержит выдуманной истории. Для loading, error, offline,
invariant validation и обновления памяти пользователь видит отдельный статус. При ошибке обновления
памяти успешная сохранённая пара и её response остаются видимыми; ошибка
сохранения самой пары не создаёт успешный response.

События пользовательских действий и основных ответов содержат correlation ID,
результат, категорию ошибки и длительность, когда она применима. Логи не
содержат secrets, credentials или неразрешённые текстовые payloads.

## Runtime-конфигурация

Backend читает YAML-конфигурации `config.yaml` и `llm.yaml`. Строковое значение
вида `${NAME}` заменяется значением переменной окружения `NAME` до YAML-разбора.
Если такая переменная отсутствует или её значение после trim пусто, запуск
завершается безопасной диагностируемой config error: имя переменной допустимо в
сообщении, её значение и содержимое YAML — нет. В этом MVP `llm.yaml`
дополнительно содержит валидную обязательную секцию `invariant_validation`; её
отсутствие безопасно останавливает запуск. Полный контракт этой секции
определяет `invariants`.

До чтения YAML `api-server` может загрузить один или несколько dotenv-файлов
повторяемым флагом `--env-file`: например, `--env-file .env --env-file
deploy/secrets.env`. Файлы обрабатываются слева направо, первое определение
переменной имеет приоритет над последующими; уже установленное окружение ОС
имеет приоритет над любым dotenv-файлом. Формат dotenv поддерживает стандартные
экспортируемые переменные, кавычки и комментарии. Секреты размещаются в
локальном `.env`, который не отслеживается Git; репозиторий содержит только
`.env.example` без значений секретов.

### Compose deployment

Для production-запуска оператор создаёт `backend/config.yaml`,
`backend/llm.yaml` и корневой `.env` из example-файлов, указывает секреты только
в dotenv-файле и запускает `docker compose up --build -d`. Compose передаёт
dotenv-файл в runtime environment `barista-api`; YAML и prompts монтируются
read-only, а dotenv-файл не включается в image или Git. Поэтому placeholders в
смонтированном YAML разрешаются backend при старте. Путь к custom dotenv-файлу
задаётся host-переменной `BARISTA_ENV_FILE`, например
`BARISTA_ENV_FILE=deploy/production.env docker compose up --build -d`.

Backend не публикует свой порт за пределы Compose-сети. `barista-web` ожидает
healthcheck `/healthz` backend; оба сервиса автоматически перезапускаются после
сбоя, кроме явной остановки оператором. State history хранится в именованном
volume и переживает пересоздание контейнеров; оператор явно предупреждён, что
`docker compose down -v` удаляет этот state.

<!-- ac-section: adaptive -->
## Адаптивность и доступность

На ширине 390 px и 1440 px навигация по проектам и чатам, сообщения и composer
не создают горизонтальную прокрутку viewport. Длинный текст корректно
переносится или получает собственную прокрутку. Все операции доступны
клавиатурой, touch и мышью; loading/error/status программно объявляются
assistive technology. Переименование проекта доступно с клавиатуры; его
validation/storage outcome программно объявляется.

<!-- ac-section: permissions -->
## Изоляция и безопасность

Владелец данных — browser-сеанс/cookie. Другой browser-сеанс не может читать,
менять или удалять его проекты, чаты и память. Браузер обращается только к
same-origin BFF; credentials и приватные адреса провайдера остаются на
server-side. Пользовательский текст является недоверенными данными и не может
менять системные правила агента.

<!-- ac-section: performance -->
## Восстановление и производительность

Принятое состояние текущего browser-сеанса переживает refresh и перезапуск
backend. Непринятый локальный ввод не восстанавливается. При offline refresh
показывает последнее принятое состояние; автоматический retry отсутствует.

Числовой latency-бюджет основного ответа не установлен, поскольку зависит от
провайдера. UI обязан показывать progress до завершения полного цикла основной
попытки и обязательного обновления памяти; проверка выполняется controlled
provider и browser-сценарием.

## Acceptance criteria

- **AC-BAR-01.** Пользователь создаёт пустой проект, создаёт в нём два чата и
  переключается между ними; сообщения одного чата не видны в другом. Проверка:
  browser + API contract.
- **AC-BAR-02.** Успешная отправка создаёт ровно одну user/assistant пару в
  выбранном чате; повторная отправка ожидающей попытки недоступна. Проверка:
  controlled provider + browser.
- **AC-BAR-03.** Ошибка основной модели сохраняет user-реплику, показывает
  actionable category и допускает только ручной retry без автоматического
  дополнительного вызова. Проверка: controlled provider.
- **AC-BAR-04.** Refresh и backend restart восстанавливают принятое состояние
  только той же cookie; другая cookie не получает его. Проверка: persistence
  integration.
- **AC-BAR-05.** На 390 px и 1440 px основная навигация и composer доступны
  клавиатурой и не создают горизонтальный overflow viewport. Проверка: browser
  accessibility test.
- **AC-BAR-06.** В composer-е с текстом, содержащим хотя бы один символ после
  trim, Enter отправляет ровно одно сообщение, Shift+Enter добавляет newline
  без отправки, а Enter во время pending не создаёт запрос. Проверка: browser +
  controlled provider.
- **AC-BAR-07.** После первого final accepted user/assistant pair выполняется
  ровно один `text` title-вызов; уже принятый response не ждёт его. Валидный
  plain-text title длиной до 60 Unicode-символов сохраняется с `success`, а
  ошибка, пустое, невалидное или длинное значение даёт первые 60
  Unicode-символов user message с `fallback`. Technical validator error и
  непринятый candidate title не запускают; retry, второе сообщение, refresh и
  restart не создают второй title-вызов. Проверка: controlled provider +
  persistence integration.
- **AC-BAR-08.** Пользователь с клавиатуры переименовывает проект PATCH-запросом
  в непустой trimmed title длиной до 100 Unicode-символов; refresh/restart
  сохраняет его, а чаты и память не изменяются. Пустой/длинный title и storage
  error сохраняют прежнее название и возвращают безопасный outcome. Проверка:
  browser + API contract + persistence integration.
- **AC-BAR-09.** Compose передаёт `.env` либо путь из `BARISTA_ENV_FILE` только
  в runtime environment backend, и `${SECURE_API_KEY}` в смонтированном
  `llm.yaml` успешно разрешается без включения dotenv-файла в image. Backend
  остаётся недоступен с host напрямую, web ждёт `/healthz`, а named history
  volume переживает пересоздание сервисов. Проверка: `docker compose config` с
  временным dotenv-файлом + ручной container smoke test.
- **AC-BAR-10.** У выбранного чата над composer-ом видны его ID и доступная с
  клавиатуры кнопка копирования; clipboard содержит только ID. После смены чата
  панель показывает его ID, а до выбора чата не показывается. Проверка: unit +
  browser.
- **AC-BAR-11.** `/admin` находит существующий чат по скопированному ID и
  показывает его журнал; неизвестный ID остаётся нейтрально не найденным.
  Запись с новым backend полем или типом вызова также неизменённо проходит через BFF.
  Проверка: API contract + BFF test + browser.
- **AC-BAR-12.** В раскрытом prompt/payload Admin семантический `\n` виден как
  перенос строки без изменения исходного payload, включая double-escaped запись.
  Проверка: component test.

Подготовка этой спецификации не включает изменения исходников, тестов,
конфигурации, runtime-данных, Git-ветки или task-артефактов.
