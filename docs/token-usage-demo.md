# Демонстрация учёта токенов

В чате под ответом показаны вход и выход из `usage` провайдера. Вход включает
system prompt, завершённую историю и новое сообщение. «Учтено токенов» суммирует
подтверждённые входы и выходы попыток основной беседы; генерация названия исключена.
История повторно отправляется на каждом шаге, поэтому накопленный расход растёт
быстрее, чем число сообщений. При отсутствии `usage` новая сумма не предполагается.

## Воспроизводимая имитация

Это проверка контракта приложения с управляемым HTTP provider, **не измерение
DeepSeek**. Fixture возвращает заранее заданные числа, а после восьми user-реплик
серии `tokens-growth-*` отклоняет следующий запрос как `context_length_exceeded`.
Числа не получены токенизацией текста. Так воспроизводится рост контекста,
накопление расхода и реакция UI на отказ провайдера.

Запуск изолированного стенда описан в [E2E README](../frontend/e2e/README.md).
На работающем стенде из `frontend`:

```sh
npm run test:e2e -- e2e/token-usage.spec.mjs
```

Для ручного повтора создайте новый диалог, последовательно отправьте
`tokens-growth-1` … `tokens-growth-9`. Модель fixture — `e2e-fixture-model`.

| Сценарий / шаг | Вход | Выход | Учтено всего | Результат |
| --- | ---: | ---: | ---: | --- |
| Короткий, 1 | 100 | 20 | 120 | Ответ |
| Короткий, 2 | 150 | 30 | 300 | Ответ |
| Длинный, 3 | 200 | 40 | 540 | Ответ |
| Длинный, 4 | 250 | 50 | 840 | Ответ |
| Длинный, 5 | 300 | 60 | 1200 | Ответ |
| Длинный, 6 | 350 | 70 | 1620 | Ответ |
| Длинный, 7 | 400 | 80 | 2100 | Ответ |
| Длинный, 8 | 450 | 90 | 2640 | Ответ |
| Переполнение fixture, 9 | Нет данных | Нет данных | 2640 | HTTP 400, `context_limit` |

После девятого шага история и ошибочная реплика остаются, assistant-ответа нет,
composer заблокирован по существующему правилу ошибок. Доступны ручной retry
и новый диалог. Тот же контекст снова приведёт к отказу fixture. Refresh сохраняет
показатели и не добавляет расход. Вызов модели названия имеет fixture usage 10000,
но эта величина не появляется в итоговом счётчике.

Дополнительные сценарии в новом диалоге:

- `tokens-missing`, `tokens-invalid`, `tokens-zero`: отсутствие/невалидная
  статистика показываются как «нет данных», подтверждённый ноль показывается числом.
- `tokens-empty-retry-<уникальное значение>`: первая попытка возвращает пустой
  список ответов с usage 100/20. Итог становится 120 несмотря на ошибку обработки;
  ручной retry получает ответ и увеличивает итог до 240 без второй user-реплики.
- `tokens-overflow`: прямое воспроизведение известного кода ошибки без заполнения
  истории. Оно проверяет обработку ошибки, но не проверяет размер контекста.

## Реальная модель DeepSeek

Используемая пользователем модель — `deepseek-v4-pro`. В официальном
[анонсе DeepSeek V4](https://api-docs.deepseek.com/news/news260424/) заявлен контекст
1M. Реальный сценарий требует отдельного изолированного чата с валидной подготовленной
историей больше этого контекста и отправки следующего сообщения через приложение.
Лимит длины формы снят; транспортный предел JSON-запроса — 32 МиБ.
Timeout, ограничение HTTP или ошибка сети не доказывают
переполнение модели. Требуется фактический ответ провайдера с причиной отказа.

Код `context_length_exceeded` встречается в
[официальном тесте адаптера DeepSeek](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/llm/llm-deepseek/tests/adapter.spec.ts).
Это основание для fixture, а не доказательство выполненного живого запроса.

В этой QA-проверке платный DeepSeek API не вызывался. Реальные короткий, длинный
и переполненный диалоги с `deepseek-v4-pro` остаются непроверенными; приведённая
таблица относится исключительно к имитации. Итог выполнения проверок записан в
[VERIFICATION.md](../.specs/barista-agent/VERIFICATION.md).
