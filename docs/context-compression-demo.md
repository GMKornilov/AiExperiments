# День 9: сравнение режимов

Включите секцию summary из backend/llm.example.yaml. N задаётся параметром
keep_last_messages, период — batch_size; оба default 10. N включает текущую
user-реплику. Системный prompt не сжимается. Между обновлениями сохраняется
до N + batch_size − 1 исходных сообщений. Summary накапливается из предыдущего
summary и очередной части истории, а не пересоздаётся из всей переписки.

Настройки фиксируются при создании диалога. Старые диалоги без настроек summary
получают их из текущего конфига при перезапуске backend; режим остаётся выключенным.
История и снимки chat/text при этом не меняются. Для сравнения создайте два новых.
В JSON полная видимая переписка хранится в dialog.messages, отдельно от
agent_messages (несжатый хвост) и summary. Агент не получает видимый архив.
Выключение сжатия сохраняет summary и запрещает новые суммаризации.
Изменение переключателя во время активной попытки запрещено. Ошибка суммаризации
делает текущую реплику доступной для ручного retry; успешный summary после ошибки
основной модели используется повторно. Сбой записи блокирует сервис как прежде.
Аварийное завершение процесса до записи результата может потребовать нового вызова.

## Качество на реальной модели

Создайте два диалога с одинаковыми настройками chat: в одном оставьте сжатие
выключенным, в другом включите. Повторите одинаковые user-сообщения (ответы модели
могут отличаться). Для короткой демонстрации задайте N=3, batch_size=2.

1. «Готовлю эспрессо. Молоко нельзя. Доза 18 г, выход 36 г, температура 93°C».
2. «Исправление: доза теперь 17 г. Выход пока 36 г. Запомни исправление».
3. «Объясни, как помол влияет на вкус, без изменения моего рецепта».
4. «Как оценивать равномерность экстракции?»
5. «Повтори мои ограничения и текущие числа. Что я исправил?»
6. «Какую одну переменную поменять, если кофе горчит? Остальные сохрани».

Оцените каждый контрольный ответ по сохранению запрета молока, актуальной дозы
17 г, выхода 36 г и температуры 93°C; отдельно отметьте выдуманные факты и потерю
исправления. Для надёжного вывода повторите несколько раз. Просмотр summary
позволяет увидеть, была ли ошибка внесена суммаризатором или основной моделью.
Реальное качество в этой реализации автоматически не оценивалось.

## Токены

Для каждого режима запишите вход и выход под каждым ответом, «Учтено токенов»
и расход суммаризации. Полная стоимость сжатого режима:
chat accounted_tokens + compression.summary_tokens; название исключено в обоих.
Экономия = 1 − (chat + summary в сжатом режиме) / chat в полном режиме.
При неизвестной статистике итог неполный; не считайте отсутствие usage нулём.
Summary может увеличить общий расход на короткой истории.

Прогресс-бар использует фактический последний prompt_tokens, включая system,
summary/историю и input. Это доля окна, занятая входом; output в неё не входит.
Размер окна берётся из chat.context_window_tokens, а не угадывается по имени модели.
Оценки до/после рассчитаны одинаково: (UTF-8 bytes текста + 16 на сообщение) / 4,
округление вверх. Для русского текста это грубая оценка; она не учитывает
точный tokenizer, служебные токены и особенности конкретного провайдера.

## Автоматическая проверка

Go-тесты проверяют порог, накопительное обновление, retry, отключение режима,
потерю usage, восстановление и отсутствие ключей в persisted JSON.
Browser-тест frontend/e2e/compression.spec.mjs проверяет весь путь через BFF,
refresh, actual input progressbar, сохранение сжатых реплик на экране и ширину 390 px.
Нужен изолированный стенд из frontend/e2e/README.md. Fixture уже содержит секцию
summary (model: e2e-summary-model, keep_last_messages: 3, batch_size: 2)
и chat.context_window_tokens: 1000.
Запуск: npm run test:e2e -- e2e/compression.spec.mjs.
Fixture возвращает синтетический summary и usage: это проверка механизма,
а не измерение качества или стоимости DeepSeek.

Проверенный результат третьего запроса fixture: оценка полной истории 1469,
отправленной 841 (снижение около 42.75%), расход summary 50 и input 200.
Последние два числа заданы fixture и не являются результатом токенизации.
